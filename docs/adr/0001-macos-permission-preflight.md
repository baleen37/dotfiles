# ADR 0001: macOS 권한을 설치 전에 점검한다

- 상태: 채택
- 날짜: 2026-11-07
- 결정·운영 책임자: dotfiles 관리자

## 배경

`./switch.sh`는 빌드 후 기존 `/Applications/1Password.app`을 Nix 관리로
옮기는 단계에서 실패했다. 실제 TCC 로그는 `dev.herdr.core`의
`kTCCServiceSystemPolicyAppBundles` 요청을 `Denied (User Consent)`로 기록했다.
root로 실행한 `install -o root -g wheel -m0555 -d`도 이 macOS 동의를 대신하지
못한다. 빌드 성공은 실제 앱 수정 권한을 검증하지 않는다.

## 결정

`bootstrap.sh`와 `switch.sh`는 선택한 호스트에 필요한 권한을 먼저 확인한다.
필수 권한이 거부됐거나 확인할 수 없으면 설정 화면과 해결 절차를 표시하고
종료 코드 1로 중단한다. 사용자가 권한을 허용하고 터미널 앱을 다시 연 뒤
같은 명령을 실행하면 다시 검사한다. 수동 완료 표시나 영구 성공 캐시는 두지 않는다.

| 확인 항목                            | 처리                                                                                                                            |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| 실행 사용자·플랫폼                   | root 직접 실행과 미지원 플랫폼을 공통 초기화에서 거부한다.                                                                      |
| 앱 관리                              | 1Password GUI 또는 Homebrew cask·App Store 앱을 선택한 Darwin 시스템에서 사전 조회한다.                                         |
| 관리자 인증·설치 도구                | bootstrap의 기존 sudo 인증·CLT·Nix 확인을 유지한다. sudo를 macOS 개인정보 권한의 대용으로 보지 않는다.                          |
| 1Password·SOPS                       | 키 설치 전에 실제 인증·개인키 형식·선언된 암호문의 복호화를 검사한다. switch는 복호화 검사 후에만 활성화한다.                   |
| 접근성·입력 모니터링 등 앱 실행 권한 | 설치 대상 앱의 권한이다. 터미널 권한으로 대신 검사하거나 일괄 승인됐다고 표시하지 않는다. 앱 설치·실행 시 해당 앱에서 승인한다. |

### 실행 순서

1. 이미 Nix가 있는 Mac의 bootstrap은 sudo·CLT·도구 빌드 전에 권한을 확인한다.
2. 새 Mac은 호스트 선택을 평가할 Nix가 필요하므로 CLT·Nix 설치 후, 나머지 도구·Homebrew·키 설치 전에 확인한다. 미등록 Mac은 기존 정책대로 최소 구성으로 등록한다.
3. switch는 구성 선택 후, 시크릿 검사·시스템 빌드·sudo·활성화 전에 확인한다.
4. Linux, standalone Home Manager, `switch.sh --build`, GUI 앱이 없는 최소 호스트에는 앱 관리 권한을 요구하지 않는다.

### 앱 관리 조회와 설정 안내

`/usr/bin/osascript`의 JXA에서 TCC의 읽기 전용 `TCCAccessPreflight`를 호출한다.
이를 `scripts/lib/macos-app-management.js`에 격리한다. 현재 프로세스의 책임 앱에
대한 결과만 사용한다. 터미널을 바꾸면 권한도 다시 확인해야 한다.

반환값 0은 허용, 1은 거부이며 나머지 값·API 없음·실행 오류는 확인 불가다.
조회에는 **비공개 SPI**를 사용하므로 향후 macOS 변경 시 깨질 수 있다. 확인 불가를
허용으로 간주하지 않는다. 실패하면 `Privacy_AppBundles` 설정 화면을 열고,
허용할 대상이 현재 터미널을 제공하는 앱(예: Herdr Core)임을 안내한다.
화면 열기 자체가 실패해도 설정 경로·URL을 출력하고 중단한다.

이 조회는 설치 완료 보장이 아니다. 실제 활성화의 오류 전파는 유지한다.
Homebrew가 별도의 책임 프로세스로 실행하는 작업, 앱별 정책 등은 별도 원인으로
실패할 수 있다. 화면을 열었다는 사실이나 사용자의 Enter 입력도 권한 허용의 증거가 아니다.

## 검토한 대안

| 대안                                 | 판단                                                                                               |
| ------------------------------------ | -------------------------------------------------------------------------------------------------- |
| 설치 실패 후에만 안내                | 긴 빌드와 부분 적용 후 실패하므로 채택하지 않는다.                                                 |
| 모든 개인정보 권한 요구              | 설치와 무관한 권한까지 요구하고 앱별 승인을 잘못 대체하므로 채택하지 않는다.                       |
| TCC 데이터베이스 읽기·수정, SIP 해제 | 추가 권한이 필요하거나 macOS 동의 경계를 우회하므로 사용하지 않는다.                               |
| 비공개 SPI 없이 수동 확인만 받기     | 구현은 단순하지만 현재 거부 상태를 자동 판별하지 못하고 잘못된 성공 확인이 가능해 채택하지 않는다. |

## 검증과 운영

CLI 통합 시나리오로 허용·거부·확인 불가·조회 오류를 검사한다. 거부 경로에서는
설정 URL 안내 후 빌드·sudo·활성화가 실행되지 않아야 한다. 최소 호스트·Linux·
standalone HM·build-only 경로는 조회와 설정 화면 열기를 실행하지 않아야 한다.
실제 Mac에서는 읽기 전용 조회와 공개 CLI의 거부 경로를 확인한다. 실제 앱 덮어쓰기와
전체 활성화는 이 검증에서 수행하지 않는다.

조회 호환성이 깨지면 이 파일과 격리된 조회 구현을 함께 수정한다. 임의로 검사를
건너뛰거나 성공으로 바꾸는 환경 변수는 추가하지 않는다. 철회하려면 공통 초기화의
사전 검사 호출을 제거하고 설치 시점의 실제 오류 안내로 돌아간다.
